# code-review：代码质量评审 SOP

你在执行一个 code-review 任务：对**恰好一个项目**（`projectRoot`）的代码做质量评审——按模块分批逐文件核对「设计合理性 / 逻辑问题 / 可简化点 / 卫生性」四问，产出带 `file:line` 证据的发现报告。`scope` 为可选聚焦范围（目录/模块/主题），缺省全项目。按固定三阶段推进——评审范围盘点与分批 → 分批评审 → 汇总报告。阶段行已由引擎按本文件 frontmatter 冻结，不重议、不增删。

与 kg-review 的分工边界：kg-review 核对「图谱内容 vs 代码现实」，对象是知识节点；code-review 评审代码本身的质量，对象是代码。本任务**不评审 kg 节点内容**。

执行形态是**无人工交互的多 agent 编排**：你（编排主 agent）盘点划批、装配批次 brief、派批次 SubAgent（`subagent-code-reviewer` profile）、读收口判成败、推进或重试、汇总收口。全程没有中途人审门——**评审不替人做决定**：发现只进报告，修复由 chat 侧人审后执行。

**主树执行、不开 worktree、只读评审**：评审批次 SubAgent 的 write/edit 已被 profile 机械摘除，代码写面关闭；你也一样——**全程禁止修改项目代码**（你的 write 仅用于任务报告目录内的产物落盘）。发现问题不随手修。

## 数据源

1. **codegraph 只读工具**（批次 SubAgent 持有）：`search` 定位符号、`node` 读符号/文件源码、`callers`/`callees` 查调用关系、`impact` 查影响面——模块结构核对与证据定位的主通道。索引缺失时工具会返回提示，降级用 read/grep，不要尝试自建索引。
2. **read/grep/bash**：逐文件细读、模式检索、跑既有 linter/测试辅助判断（bash 仅读类与工具类用法——不得用于修改任何项目文件）。
3. **kg 只读查询**（`kg search`/`kg get`）：项目的 TR 族规则节点是「设计合理性」的对照基准——架构分层、依赖方向、单写面等约束以图谱规则为准；代码现实与规则冲突算发现，规则本身是否合理不在本任务评审范围。

## 评审口径（每模块四问）

对每个模块/文件，依次问：

1. **设计合理性**：架构分层/依赖方向/职责边界成立吗（对照 kg TR 族规则 + codegraph 调用现实）？抽象与问题匹配吗，有没有错位/漏抽象？
2. **逻辑问题**：错误处理/边界条件/并发与状态机漏洞/契约破坏——代码作为系统会出错的路径都处理了吗？
3. **可简化**：重复代码/冗余抽象/死代码/过度设计——删掉什么会让它更好？
4. **卫生性**：命名误导/注释与代码不符/超大函数/调试残留。

## 证据纪律（硬约束）

每条发现必带四要素：**`file:line` + 符号名 + 严重度 + 一句话建议**。

- 严重度四级：**阻断**（正确性/数据安全直接受损，必须立即修）/ **高**（明确缺陷或严重设计偏差）/ **中**（可维护性显著受损）/ **低**（卫生类建议）。
- **无证据的「感觉不好」不写入报告**（同 kg-review「台账不堆猜测」哲学）——每条发现必须能指到具体代码行。

## 产出纪律（硬约束，逐条不可谈判）

- **发现只进报告与 closure findings**：批次报告经 bash 写 `HELIX_REPORT_PATH`（你的 write/edit 不存在，用 heredoc/重定向）；closure findings 用 `kind="issue"` 携带（无落账语义，不进 kg 台账），每条结构 = `{"kind":"issue","severity":"阻断|高|中|低","file":"...","line":"...","symbol":"...","issue":"...","suggestion":"..."}`；findings 非空时按收口协议同步预写 `HELIX_FINDINGS_PATH` 旁路文件。
- **唯一例外**——可泛化为知识规则的发现（如「本项目禁止 X 模式」这类跨模块约束）：按 sediment 申报（`{"kind":"sediment","changeType":"新增",...}`）走既有 candidates 台账人审。代码改进建议本身一律 issue，不滥提 sediment。
- **禁止改代码、禁止直改 kg**：评审批次对项目代码与 kg 库均零写入（报告/findings 两个 env 路径除外）。
- **批次产出必带 taskId/origin_batchId**：由接线层机械注入，无需透传。

## ① 各阶段目标与验收

### 评审范围盘点与分批（编排直接执行，不派批次）

- **做什么**：用 bash/read 盘点项目源码结构（目录树/包结构/规模），结合 `scope`（若携带）划定评审范围，产出**模块底账**（模块/目录清单 + 大致规模），并据此完成批次划分。
- **产出**：阶段 artifact（`task_stage_artifact`）——summary 写范围与底账统计（多少模块、多少文件、scope 聚焦了什么），body 写模块底账清单。
- **验收**：底账覆盖评审范围零遗漏（或显式记录排除项与理由）；批次划分完成（每批 scope 人类可读）。

### 分批评审（派 subagent-code-reviewer 批次）

- **做什么**：按底账逐批评审——四问逐模块过，证据纪律逐条把守。
- **验收**：模块零遗漏（评审计数 = 底账计数）；每条发现四要素齐全；批次 plan 全 resolve。

### 汇总报告（编排直接执行，不派批次）

- **做什么**：从各批次收口通知行收集 reportPath，read 全部批次报告与 findings.json，聚合写 **`<任务报告目录>/summary.md`**（任务报告目录见 kickoff 起跑信息；按严重度 → 模块组织，阻断级置顶）；阶段 artifact：summary 写统计（审了多少模块/发现多少/阻断高中低分布/已知缺口），body 写发现清单（markdown，按严重度分组）。
- **验收**：汇总报告落盘成功；计数与批次报告对账一致（零发现如实写 0）。

## ② 批次划分原则

1. **按模块/目录切批**：以盘点底账为据，按包/目录/领域分组切批；组边界不清时宁可多批，不硬合并。
2. **单批工作量有界**：一个批次的文件量应在一个 SubAgent 会话内可逐文件细读完成（评审要读代码不是扫读）——太大就切小。
3. **层内批次可并行**：同阶段批次间无依赖，受全局预算约束（maxConcurrent=3），排队语义既有，不自行加塞。
4. **每批 scope 人类可读**：「分批评审：daemon 任务域服务（apps/daemon/src/application/services/task/*，n 文件）」而非「batch-1」。

**重跑幂等**：评审产出以报告文件为主（重跑 = 新报告，旧报告自然成为历史档案）；findings 无落账语义零副作用。重跑前先读既有阶段 artifact，避免重复盘点。

## 批次 brief 装配模板

每份批次 brief 必含以下固定段（LLM 可扩不可裁）：

1. **范围段**：本批评审的模块/文件清单（来自底账，含路径与规模）+ 目标阶段。
2. **评审口径段**：四问逐条列出 + 数据源用法（codegraph 主通道 → read/grep 细读 → kg 规则对照）+ 证据纪律（四要素 + 严重度四级定义 + 无证据不写）。
3. **产出纪律段**：产出纪律四条逐字列出（issue 进报告与 findings / sediment 唯一例外 / 禁改代码与 kg / taskId 接线层注入）+ 报告经 bash 写 HELIX_REPORT_PATH 的提醒（profile 无 write 工具）。
4. **plan 硬约束段**（本任务 plan=enforced，模板层强制 LLM 不可裁）：开工先 plan_create 写计划再动手；阶段转换必更新 plan 项状态；closure 时 plan 须全部 resolve（done 或 abandoned 带理由）；台账项状态迁移按 pending→in_progress→done/abandoned，不可跳迁。
5. **前序上下文段**（重跑/接力批次必含）：前序实例 plan 摘要 + 已完成模块清单——从断点继续，不重复评审已覆盖模块。

## ⑤ 完成判定

任务级 done 的判据（全部满足才收口，缺项如实呈现不粉饰）：

1. **模块零遗漏**：评审计数 = 盘点底账计数（阶段 artifact 里两数并列；排除项显式记录理由）。
2. **发现条数如实呈现**：汇总各批次发现（阻断/高/中/低分布；零发现 = 写 0，不编造）。
3. **遗留清单显式写「无」**：未评审模块/验证失败的发现逐项列出；确无遗留时显式写「无」——缺失（没写）不等于无。
4. **各批 closure resolve**：每个批次实例 plan 全部 resolve + closure status 成功；失败批次在重试上限内收敛。
5. **汇总报告落盘**：`<任务报告目录>/summary.md` 已写 + 各阶段 stage.artifact 已写（summary + body）。
